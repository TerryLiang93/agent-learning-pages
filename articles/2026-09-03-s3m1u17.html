评估与调试：怎么知道 Agent 好不好

2026-09-03 · 协作与质量 · 预计 30 分钟

今日要点

今天学的是怎么判断你做的 Agent 到底行不行。就像焊完一块板子要测电压、看波形一样，Agent 写完也要有测试方法。你会学到三个词：评估集（准备一堆考题）、回归测试（改完代码全考一遍）、日志（看 Agent 干活时的"黑匣子"）。核心就一句话：不能凭感觉说"好像能用"，要用数据说话。

术语卡片

  • 评估集 —— 就像你给 Agent 准备的一摞"考试卷子"。每张卷子是一个任务，提前写好了标准答案或评分标准。以后每次改代码，都拿这摞卷子重新考一遍。
  • 指标 —— 把"好不好"变成数字。比如：10 道题做对了几道（正确率）、一道题花了多少钱（成本）、答得流不流畅（质量分）。没数字就没法比较。
  • 回归测试 —— 改完一个 bug，最怕的是把原来好用的功能搞坏了。回归测试就是"把以前的考题全部重跑一遍"，确保新改动没破坏旧功能。就像你换了板子上的电容，得把之前的测试全再做一次。

原理精讲

为什么不能靠"感觉"？

假设你让 Agent 帮你写一个 Python 脚本处理日志文件。你试了三次，感觉"挺聪明的"。但第四次它突然卡住了——因为这次的日志格式多了一种你没见过的时间戳。

问题在于：你的"感觉"来自少数几次成功。你不知道它在 100 次里能成功几次，也不知道哪些场景会翻车。

评估集就是你的"测试治具"

做硬件时，你要测一块电源板，会准备不同的负载（10% 负载、50% 负载、满载）。Agent 也一样——你要准备不同类型的任务：

  • 简单任务：提取日志里的错误信息
  • 中等任务：把日志按时间排序并去重
  • 困难任务：根据日志内容自动生成故障分析报告

每个任务后面写上"什么算对"。可以是精确答案，也可以是一个打分标准（比如"是否包含了错误码和发生时间"）。

改一次，全考一遍（回归测试）

你改了一行 prompt，让它回答更简洁。结果发现：简洁是简洁了，但原来会做的数学题现在不做了——因为它把"步骤"也省了。

没有回归测试，你根本发现不了这个问题。有了它，一跑就知道：数学题挂了 3 道。马上回滚。

日志：Agent 的飞行记录仪

飞机上有黑匣子，Agent 也应该有。日志就是记录 Agent 每一步干了什么：它调了什么工具、传了什么参数、返回了什么结果、它自己说了什么"思考过程"。

遇到问题，不要盯着最终输出猜。打开日志，看它哪一步开始跑偏的——是理解错了需求？还是调工具时参数传错了？还是结果处理不对？就像查硬件故障，先看示波器波形在哪一段失真。

动手任务

手机任务（5 分钟）

打开你手机里的备忘录，列出你平时让 AI 助手做的 5 类任务（比如：写周报、翻译、解释概念、写代码片段、总结文章）。每类任务写 1 个具体例子和你认为"算对"的标准。这就是你的第一版"评估集"草稿。不用完美，先有 5 条。

电脑任务（10 分钟）

如果你已经有正在开发的 Agent 或自动化脚本：

  1. 建一个 tests/ 文件夹，里面放一个 evaluation.md 文件
  2. 写 3 个测试用例，格式如下：
    3.    ## 用例 1：提取错误日志
   - 输入：一段包含 3 个 ERROR 和 5 个 INFO 的日志文本
   - 期望输出：只包含 ERROR 行，且按时间排序
   - 通过标准：输出中无 INFO 行，ERROR 行数 = 3
  3. 在你的 Agent 主代码里，每个关键步骤加一行 print(f"[STEP] 正在执行: {步骤名}") 或使用 logging.info()

做完这两件事，你就有了最基础的"评估集 + 日志"。

AI 工具箱

今日推荐：用"机械检查"给 AI 输出把关 —— 从 consulting-pptx-skill 学到的思路

【这是什么】GitHub 上一个叫 gozen3ji/consulting-pptx-skill 的项目（⭐63），它的核心思路是：让 AI 做 PPT，但不信任 AI 的自觉——生成完后用一套机械规则自动检查结果。

【有什么用】AI 写代码、写文档、做 PPT，经常"看起来对但细节全错"。手动检查太累，让机器替你查。

【怎么用】它的做法分三步：

  1. 定规矩：先把规则写成文件（比如 PPT 必须用 38 种版式之一，标题不能超过 20 字）
  2. AI 干活：让 AI 按规矩生成内容
  3. 机械检查：写一个脚本检查输出是否符合规则（有没有用未定义的版式？字号对不对？），不通过就打回重做

【实用例子】你可以把这个思路用在日常：让 AI 写代码后，用一个 grep 命令检查有没有把 print() 留在生产代码里；让 AI 写文章后，用一个脚本检查有没有出现"首先、然后、最后"这种废话开头。规则越具体，机械检查越有效。这比反复改 prompt 靠谱得多。
