错误处理与重试：让 Agent 不轻易崩溃

2026-09-05 · 真实落地 · 预计 30 分钟

今日要点

今天学的是"让 Agent 不轻易崩溃"。你写程序时，调用外部 API 可能超时、工具可能报错、模型可能返回乱七八糟的内容——这些都是常态。关键不是避免出错，而是出错后程序还能活着，给用户一个合理的交代。这就是容错、重试、降级这套东西要解决的问题。

术语卡片

  • 重试 —— 事情没办成，再试一次。就像打电话占线，过几秒再拨。
  • 超时 —— 等太久了，不等了。就像你等外卖，等了 2 小时还没到，你不可能一直等下去，直接取消订单。
  • 降级 —— 主方案不行了，换备胎方案。就像主路堵死了，走辅路绕过去。
  • 容错 —— 系统对错误的"容忍能力"。就像人摔了一跤能爬起来接着走，而不是直接躺平。

原理精讲

为什么 Agent 特别容易崩？ 因为 Agent 不像普通程序只调自己的代码，它要调外部 API、要调工具、要调模型——这些都是"不可控"的。你没法保证对方一定响应、一定正确。

核心思路就三层：

第一层：超时控制。 给每次调用设一个时间上限。比如调天气 API，最多等 5 秒，5 秒没回来就放弃这次调用。没有超时控制，程序可能永远卡在那里等——这叫"死等"，是最低级的错误。

第二层：重试。 超时或报错后，别急着放弃，再试几次。但要注意：不能立刻重试。如果对方服务器正忙，你立刻再打过去大概率还是忙。所以要"指数退避"——第一次等 1 秒再试，第二次等 2 秒，第三次等 4 秒，越等越久，给对方喘息的时间。同时设个最大次数，比如 3 次，试完还不行就放弃。

第三层：降级。 重试也失败了怎么办？不能就这么崩了。要有备选方案。比如：

  • 调天气 API 失败 → 改用另一个免费天气 API
  • 两个 API 都失败 → 告诉用户"天气服务暂时不可用，请稍后再试"，而不是抛出一堆错误堆栈

降级的核心原则：给用户一个能用的结果，或者一个清楚的交代，而不是崩溃。

生活化类比： 你让助手去楼下买咖啡。助手发现那家店关门了（失败），他不会直接回来跟你说"我失败了"然后走人——他会去另一家店买（降级）。如果所有店都关门了，他会回来告诉你"今天楼下所有咖啡店都关门了，我试了 3 家"（如实告知），而不是空手回来一脸懵。

动手任务

手机任务（5 分钟）： 回想你最近用过的手机 App——比如外卖软件。当网络不好时，它是不是会显示"加载失败，点击重试"？观察一下：它失败后是立刻让你重试，还是等了一会儿？如果一直失败，它最后显示什么？把观察结果写下来，这就是真实世界里的容错设计。

电脑任务（5 分钟）： 如果你已经写过调用 API 的 Agent 代码，检查一下你的代码里有没有这三样东西：

  1. 有没有设超时？（比如 timeout=10 这样的参数）
  2. 有没有重试逻辑？重试之间有没有等待？
  3. 如果最终失败了，程序是抛异常崩溃，还是能优雅地告诉用户"出错了"？

如果三样都没有，你的 Agent 就是一个"脆皮 Agent"——一碰就碎。至少先加上超时参数，这是最简单的一步。
