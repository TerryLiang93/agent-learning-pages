多 Agent 协作：分工与沟通

2026-09-02 · 协作与质量 · 预计 30 分钟

今日要点

今天学的是多 Agent 协作——说白了就是让好几个 AI 一起干活，像公司里一个项目组分给不同的人做。你不需要会写代码，重点是理解"为什么要拆分""谁来指挥谁""消息怎么传"。学完今天，你能设计一个简单的多 Agent 分工方案，说清楚每个 Agent 干什么、听谁的。

术语卡片

  • 多 Agent —— 多个 AI 程序同时工作，各管一段，合起来完成一个大任务。就像工地上的塔吊、钢筋工、瓦工，不是一个全能工人在干所有事。
  • 编排 —— 由一个"总指挥"决定哪个 Agent 先干活、干完传给谁、谁的结果需要合并。就像项目经理排工序。
  • 主从模式 —— 一个"主管" Agent 负责拆任务、发指令、收结果，其他"从属" Agent 只干活不决策。类似组长带组员。
  • 消息传递 —— Agent 之间互相传数据/指令的方式，相当于同事之间发工作交接单。

原理精讲

为什么一个 AI 不够用？ 想象你让一个实习生独立做一个完整的产品：调研、设计、写代码、测试、写文档。他要么做得很浅，要么某一块特别强其他很弱。多个 Agent 的道理一样：一个擅长写代码、一个擅长查资料、一个擅长检查错误，各干各的强项，整体质量更高。

三种常见协作模式（用做饭打比方）：

  1. 主管分配（主从模式）：你（用户）是老板，主 Agent 是厨师长。厨师长把"做一桌菜"拆成"洗菜、切菜、炒菜、摆盘"，分别派给帮厨，最后汇总。帮厨之间不直接沟通，都向厨师长汇报。
  1. 专家各管一块（流水线）：一个 Agent 只做"切菜"，切完传给下一个"炒菜"的，再传给"摆盘"的。每个 Agent 只关心自己这一步，输入是什么、输出是什么。这种也叫 pipeline 模式。
  1. 互相传递结果（讨论式）：Agent A 提出方案，Agent B 审查并提意见，Agent A 根据意见修改，再来回几轮。像两个工程师互相 code review。

核心问题：沟通成本与失控风险。 人越多开会越乱，Agent 也一样。每个 Agent 之间传消息都要时间，消息格式不一致会解析失败，指令含糊会让 Agent 各自理解不同导致结果对不上。更危险的是"失控"——某个 Agent 跑偏了，主管没发现，后面所有 Agent 都在错误基础上继续干活，最后结果全错。所以设计多 Agent 系统时，分工边界要清晰、消息格式要固定、要有检查点。

动手任务

手机任务（5 分钟）：拿出一张纸（或手机备忘录），设计一个"多 Agent 写产品说明书"的方案：

  • 写清楚：需要几个 Agent？各自负责什么？谁是指挥？结果怎么汇总？
  • 参考答案方向：主管 Agent 拆大纲 → 资料收集 Agent → 文案撰写 Agent → 校对 Agent → 汇总给主管。

电脑任务（5 分钟，可选）：如果你电脑上装了任何 AI 编程工具（如 Cursor、Codex CLI），做一个最简单的实验——让一个 Agent 写一段 Python 代码，再让另一个 Agent（或同一工具的另一个会话）审查这段代码的 bug，然后把审查结果传回给第一个 Agent 修改。观察"消息传递"的过程。

AI 工具箱

主题：Agent 编排的新趋势——"项目大脑"（Project Brain）

【是什么】 一种新架构：所有 Agent 共享一个"项目记忆库"（通常是一个结构化的知识图谱），而不是靠互相传消息。每个 Agent 干活前先读这个库，干完把结果写进去。

【为什么火】 多 Agent 最大的问题是消息传着传着就乱了、上下文丢了。共享记忆库相当于大家看同一块白板，谁改了什么一目了然，不用来回传话。

【核心要点】 ① 项目目标、决策、风险、需求都记录在共享库里，任何 Agent 随时可查；② Agent 之间不直接对话，只跟"库"对话，减少沟通成本；③ 人类也能读这个库，随时知道 AI 在想什么、做到哪一步了。相关项目：Compilr.dev Studio（搜索关键词：Compilr.dev Studio project brain）。
