自己写一个'对话循环'

2026-08-21 · 环境准备 · 预计 30 分钟

今日要点

今天咱们干一件特别有成就感的事：写一个能连续聊天的程序。你可能会想，聊天谁不会？但关键在于，我们要亲手搞明白"多轮对话"是怎么实现的——说白了，就是把之前说过的所有话，每次都打包一起发给AI，让它"记得"上下文。学完今天，你就能解释为什么AI聊天有时候会"失忆"，以及为什么聊得越长越费钱。

术语卡片

  • 消息列表 —— 就是一个"聊天记录本"。程序里是一个列表，里面装着每一轮你说的话和AI回的话，按顺序排好。每次问AI，都要把这个本子从头到尾递给它看。
  • 多轮对话 —— 就是你一句、AI一句，来回聊好几轮。AI能接上话，靠的不是记性好，而是我们每次都把之前的聊天记录一起发过去。
  • 历史消息 —— 就是之前已经聊过的那些内容。它们不是被AI"记住"了，而是被我们"重新发"给它了。这是理解今天所有内容的关键。

原理精讲

想象一下这个场景：你给一个完全失忆的朋友打电话。你问他"我昨天说想吃啥来着？"他肯定答不上来，因为他根本不记得昨天的事。但如果你把昨天的聊天记录拍照发给他，他看一眼就能回答你了。

大语言模型【术语】就像一个"用完即忘"的天才——它的"记忆"只存在于当前这一次计算里，对话一结束，它就什么都不记得了。

那怎么让它实现多轮对话呢？答案特别朴素：每次提问时，把之前的聊天记录一字不差地附在后面，一起发给它。

比如你问：

  1. "帮我推荐一部电影"
  2. "那部太吓人了，换一个"

第二次提问时，程序实际发给模型的不是只发"那部太吓人了，换一个"，而是发：

用户：帮我推荐一部电影
AI：（第一次的回答）
用户：那部太吓人了，换一个

模型看到完整的"对话剧本"，自然就知道"那部"指的是哪部了。这就是多轮对话的全部秘密。

所以"历史消息"不是什么神奇的记忆功能，而是一个"每次全量重发"的笨办法。 这也解释了为什么聊天越长，花钱越多——因为每次都要把越来越多的历史记录重新算一遍。

动手任务

手机任务（5分钟）

打开任意一个AI聊天App（比如ChatGPT、Kimi、豆包都行），做一个小实验：

  1. 先问它："我喜欢科幻片，帮我推荐一部电影。"
  2. 等它回答后，再问："那部太沉重了，换一个轻松点的。"
  3. 观察它是否知道"那部"指的是什么。
  4. 再开一个新对话，直接问"那部太沉重了，换一个轻松点的"，看看它是什么反应。

你会发现：新对话里它完全懵了。恭喜你，你刚刚亲手验证了多轮对话的原理——上下文只在消息列表里，不在模型脑子里。

电脑任务（10分钟）

需要电脑上装有 Python 3。没装的话去 python.org 下载安装即可。

创建一个文件 chat.py，复制以下代码：

# 这个程序需要一个 API key，没有的话可以先看代码理解逻辑
# 用 OpenAI 兼容接口，其他厂商的 API 也基本通用

from openai import OpenAI

client = OpenAI(api_key="你的API-KEY")  # 换成你的key

# 这就是"消息列表"——整个程序的核心
messages = []

print("开始聊天吧！输入 exit 退出。")

while True:
    user_input = input("你：")
    if user_input == "exit":
        break

    # 把用户的话追加到消息列表
    messages.append({"role": "user", "content": user_input})

    # 把整个消息列表发给模型
    response = client.chat.completions.create(
        model="gpt-4o-mini",  # 便宜的模型，够用
        messages=messages
    )

    # 取出AI的回答，追加到消息列表
    ai_reply = response.choices[0].message.content
    messages.append({"role": "assistant", "content": ai_reply})

    print(f"AI：{ai_reply}")

运行方法：

pip install openai
python chat.py

运行后试试连续聊几句，比如：

  • 你：我叫小明
  • 你：我叫什么名字？

第二句它应该能答上来。这就是多轮对话。

然后做个观察实验：把消息列表 messages 里加一句 print(len(messages))，看看每次对话后列表长度怎么变。列表越长，发给模型的内容越多，花钱越多——这就是"上下文变长后的成本问题"。
